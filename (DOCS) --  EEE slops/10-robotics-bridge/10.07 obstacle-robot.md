# 10.07 - Autonomous Obstacle Avoidance: Reactive Navigation and Kinematic Evasion

## 1. The Subsumption Architecture Paradigm

Autonomous obstacle avoidance does not require complex path planning or global mapping (SLAM). For lightweight embedded systems, navigation is handled via **Reactive Control**—specifically, a simplified Subsumption Architecture.

In this paradigm, the robot operates continuously in a default state (moving forward). Sensor data acts as hardware interrupts, subsuming (overriding) the default behavior with higher-priority survival behaviors (braking, evading) only when spatial thresholds are breached.

---

## 2. Detection Geometry and Braking Physics

Before a robot can evade, it must mathematically guarantee it has enough physical space to halt its kinetic momentum before colliding with the detected obstacle.

### 2.1 The Safe Threshold Calculus ($D_{\text{safe}}$)

The minimum safe detection threshold is not arbitrary; it is governed by the kinematic equations of motion. The robot must factor in processing latency (reaction time) and mechanical deceleration.

$$D_{\text{safe}} = (v_i \cdot t_{\text{proc}}) + \frac{v_i^2}{2 \cdot \mu \cdot g}$$

Where:

* $D_{\text{safe}}$ = The absolute minimum distance required to stop ($\text{m}$).
* $v_i$ = Initial forward velocity of the robot ($\text{m/s}$).
* $t_{\text{proc}}$ = Processing latency (Sensor ping time + MCU execution cycle time) in seconds.
* $\mu$ = Coefficient of kinetic friction between the tires and the floor.
* $g$ = Acceleration due to gravity ($9.81 \text{ m/s}^2$).

*Application:* If the ultrasonic sensor reads a distance $d < D_{\text{safe}}$, the robot must immediately drop into a critical hardware brake state, bypassing all other logic.

## 3. Finite State Machine (FSM) Navigation Logic

Reactive evasion is best implemented as a **Finite State Machine (FSM)**. The system exists in exactly one state at any given microsecond. State transitions are triggered by sensor boolean logic.

```text
> OBSTACLE AVOIDANCE FINITE STATE MACHINE

                      [ Start ]
                          │
  ┌────────────────►[ STATE_FORWARD ]◄─────────────────┐
  │                       │                            │
  │                 (d < D_safe)                       │
  │                       ▼                            │
  │                 [ STATE_HALT ]                     │
  │                       │                            │
  │            (Servo Sweep L and R)                   │
  │                       ▼                            │
  │               [ STATE_DECIDE ]                     │
  │               /               \                    │
  │       (Left Clear)         (Right Clear)           │
  │           /                       \                │
  │   [ STATE_TURN_LEFT ]      [ STATE_TURN_RIGHT ]    │
  │           │                       │                │
  └───────────┴───────────────────────┴────────────────┘

```

### 3.1 Servo-Mounted Sensor Sweeping

Instead of mounting multiple static ultrasonic sensors (which consume excessive GPIO and timer interrupts), a single HC-SR04 is often mounted on a 180° micro-servo (e.g., SG90).
Upon entering `STATE_HALT`, the FSM triggers a sweep:

1. Servo rotates to $180^\circ$ (Left). Acquires $D_{\text{left}}$.
2. Servo rotates to $0^\circ$ (Right). Acquires $D_{\text{right}}$.
3. Servo returns to $90^\circ$ (Center). FSM compares variables.

## 4. Differential Steering Kinematics for Evasion

Once the FSM dictates a turn direction, the chassis must execute a precise rotation to clear the obstacle. For differential-drive robots (two independent drive wheels), we utilize angular kinematics.

### 4.1 The Point Turn (Zero-Radius Turn)

For tight environments, the robot rotates around its exact center axis. This is achieved by driving the wheels at equal speeds in opposite directions.

$$V_{\text{left}} = -V_{\text{right}}$$

To calculate the exact time ($\Delta t$) required to turn a specific angle ($\theta$, in radians), we use the wheel baseline ($B$, distance between wheels) and wheel radius ($r$):

$$\Delta t = \frac{\theta \cdot B}{2 \cdot r \cdot \omega_{\text{wheel}}}$$

Where:

* $\omega_{\text{wheel}}$ = Angular velocity of the wheel (radians per second).

### 4.2 The Arc Turn (Sweeping Evasion)

For high-speed environments where coming to a dead stop is inefficient, the robot executes an arc. One wheel continues forward while the other slows down.

$$V_{\text{left}} > V_{\text{right}} \implies \text{Robot arcs to the Right}$$

The radius of the turning arc ($R$) is determined by the ratio of the wheel velocities:

$$R = \frac{B}{2} \cdot \left( \frac{V_{\text{left}} + V_{\text{right}}}{V_{\text{left}} - V_{\text{right}}} \right)$$

## 5. Bare-Metal C++ FSM Firmware

This firmware constructs a non-blocking FSM using hardware timers (`millis()`), ensuring the microprocessor is never trapped in a `delay()` loop.

```cpp
#include <Arduino.h>

// Kinematic Thresholds
const int D_SAFE = 20; // cm

// System States
enum RobotState {
    FORWARD,
    HALT,
    SCANNING,
    EVADING
};
RobotState current_state = FORWARD;

// Hardware Abstraction Stubs (Defined in previous modules)
float read_ultrasonic();
void set_motors(int left, int right);
void sweep_servo(int angle);

// State Variables
unsigned long state_timer = 0;
float d_left = 0, d_right = 0;

void execute_fsm() {
    float distance = read_ultrasonic();

    switch (current_state) {
        case FORWARD:
            if (distance < D_SAFE) {
                set_motors(0, 0); // Hard Brake
                current_state = HALT;
                state_timer = millis();
            } else {
                set_motors(150, 150);
            }
            break;

        case HALT:
            // Wait 200ms for kinetic momentum to fully stop
            if (millis() - state_timer > 200) {
                current_state = SCANNING;
            }
            break;

        case SCANNING:
            // Blocking abstraction for spatial mapping
            sweep_servo(180);
            delay(300); // Allow servo to reach physical position
            d_left = read_ultrasonic();
            
            sweep_servo(0);
            delay(300);
            d_right = read_ultrasonic();
            
            sweep_servo(90); // Return to center
            
            current_state = EVADING;
            state_timer = millis();
            break;

        case EVADING:
            // Execute Point Turn based on scan logic
            if (d_left > d_right) {
                set_motors(-150, 150); // Turn Left
            } else {
                set_motors(150, -150); // Turn Right
            }
            
            // Assume turn takes 400ms (Must be tuned to physical chassis)
            if (millis() - state_timer > 400) {
                current_state = FORWARD;
            }
            break;
    }
}

void loop() {
    execute_fsm();
}

```

## 6. Summary Checklist

1. **Reactive Subsumption:** Avoidance logic must operate as a strict override priority, instantly severing standard navigation (like line-following) when a threshold is breached.
2. **Kinematic Thresholding:** Never hardcode arbitrary stop distances. Calculate $D_{\text{safe}}$ using vehicle mass, velocity, and traction to prevent inertial collisions.
3. **FSM Enforcement:** Use `switch/case` Finite State Machines. Never write nested `if/else` loops for navigation; they lead to unpredictable deadlocks and untraceable bugs.
4. **Non-Blocking Architecture:** With the exception of physical servo sweeping constraints, navigation code must use delta-time (`millis()`) logic. Utilizing `delay()` blinds the CPU to incoming sensor data.
5. **Point Turn Implementation:** For dense obstacle fields, always execute zero-radius point turns ($V_{\text{left}} = -V_{\text{right}}$) rather than arcs, minimizing the required evasion envelope.
6. **Servo Hysteresis:** When using a servo-mounted sensor, introduce a delay between sending the PWM command and firing the ultrasonic ping to account for the physical transit time of the servo gears.
